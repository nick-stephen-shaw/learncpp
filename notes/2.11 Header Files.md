Used in place of forward declarations, which, when scaled would be extraordinarily tedious 

Header files will end with .h, .hpp. or nothing 

\#include headerfile.h

Header files consist of two parts:
1. A header guard -- more on this in the next lesson
2. The actual content of the header file
	1. Includes forward declarations for all of the identifiers we want other files to be able to see

The process for adding a header file to a project is the same as adding a code file
- see  [[2.8 Programs with Multiple Files]]

Naming conventions:
- .h is the most common extension for header files
- If a header file is paired with a source file match their base names
	- Ie) if a header file is written for add.cpp, name it add.h

For now, only put declarations and not definitions inside of header files. Putting a definition in a header file, then \#including that header file in several source files will result in a violation of the one definition rule
- see [[2.7 Forward Declarations and Definitions]]
Note that there are certain definition types that may be placed in header files, but these will be covered later on, and are only safe to be place in header files as they are exempt from the ODR

It is best practice to, although redundant, \#include header files in their paired source files since it allows the compiler to catch errors 

Do not \#include .cpp files

<> are used when its a header file we didn't write 
- for example, iostream
"" are used when it is a header file we wrote

Header files can and will often \#include other header files

- This may result in including other header files transitively, which means they are \#included but not directly -- this is fine and unavoidable if you do not use these transitively included files, but if you do require their use it is best practice to simply \#include the specific header file directly, just for future compatibility and whatnot
